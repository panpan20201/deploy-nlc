# Архитектура

## Цепочка данных

```
ссылка Encar / KB Chachacha
   │
   ├─► encar_parser / kbchachacha_parser ──► госномер, комплектация, VIN объявления
   │
   ├─► Carmoodo (Appium, планшет) ──────► VIN
   │        │
   │        └─► PARTSNUMBER (Playwright + VMware Horizon) ──► детали, дата выпуска
   │                                        ▲
   │                          работает параллельно с HeyDealer
   │
   └─► HeyDealer (Appium, планшет) ─────► история ремонта
                │
                └─► DeepL ──► перевод корейских терминов
```

Carmoodo идёт первым, потому что от VIN зависит PARTSNUMBER. Как только VIN
получен, PARTSNUMBER работает в фоне: он использует браузер, а не планшет,
поэтому выполняется одновременно с HeyDealer.

Развёртывание локальное: планшет физически подключён к компьютеру по USB,
и бот, Appium и планшет работают на одной машине.

## Ядро: `pipeline.py`

**Пайплайн никогда не падает целиком.** Каждый шаг возвращает `StepResult`
и не выпускает исключения наружу. Что удалось получить, пользователь
увидит; про остальное будет сказано, почему не получилось.

**Каждый шаг повторяется** (`STEP_ATTEMPTS = 2`), и между попытками сессия
создаётся заново: почти любой сбой оставляет приложение на постороннем
экране, и повтор в той же сессии упёрся бы в то же состояние.

**У всего есть предел по времени:** таймаут одной команды Appium
(120 секунд), `STEP_TIMEOUTS` на шаг и `REQUEST_BUDGET_SEC` на запрос.

**Кешируются только успешные результаты**, со сроками по видам данных.

### `StepResult`

```
"ok"     данные получены
"empty"  штатный отрицательный ответ (машины нет в базе, истории нет) —
         повтор ничего не изменит
"error"  техническая неудача — повтор имеет смысл
```

### Блокировки и потоки

- `_device_lock` — планшет: Carmoodo и HeyDealer работают строго по
  очереди. Appium не допускает двух сессий на одном устройстве: создание
  второй молча обрывает первую.
- `_partsnumber_lock` — одна сессия Horizon на всех.

Playwright в синхронном режиме привязан к потоку, в котором создан,
поэтому у PARTSNUMBER собственный пул из одного потока; при закрытии
сессии этот поток заменяется новым. Appium такой привязки не имеет и
работает в общем пуле.

`run_in_executor` не переносит `contextvars`, поэтому код проверки
копирует контекст вручную — иначе код проверки терялся бы в строках лога
из потоков.

По таймауту зависший вызов не прерывается сам (`task.cancel()` поток не
останавливает), поэтому сессия принудительно закрывается из другого
потока, а блокировка удерживается до завершения вызова.

## База данных: `storage.py`

`vehicles.db` (SQLite, WAL) — главный накопленный актив: при дневных
лимитах каждая запись экономит запрос к сервису.

| Раздел | Срок | Почему |
|---|---|---|
| `vin` | бессрочно | Выбит на кузове, не меняется |
| `parts` | бессрочно | Выводится из VIN |
| `repair` | `REPAIR_HISTORY_TTL_DAYS` (30) | Может пополниться |

Слова «обнови» / «заново» / «перепроверь» рядом со ссылкой включают
принудительную перепроверку.

## Лимиты: `usage.py`

| Сервис | Лимит | Привязан к | Как снимается |
|---|---|---|---|
| HeyDealer | 10 проверок в сутки | рекламный ID Google | сбросом рекламного ID |
| Carmoodo | 30 запросов в сутки | аккаунт | в полночь |

**Правило двух подтверждений (Carmoodo).** Признак «лимит исчерпан»
косвенный, а блокировка до полуночи отключает и VIN, и PARTSNUMBER.
Поэтому лимит считается исчерпанным только после двух подтверждений
подряд.

**Предохранители сброса рекламного ID** (`MAX_ADS_RESETS_PER_DAY`,
`MIN_SECONDS_BETWEEN_ADS_RESETS`) защищают от зацикливания автоматики при
ошибочном распознавании экрана лимита.

### Автоматическое снятие лимита HeyDealer

1. Вместо результата появляется экран `하루 최대 10대까지 조회 가능해요`.
2. `heydealer_history.looks_like_daily_limit()` распознаёт его.
3. `_interpret_heydealer` возвращает `StepResult("empty", reason="daily_limit")`.
4. `_recover_heydealer_limit()` проверяет предохранители, закрывает сессии
   на планшете и вызывает `ads_id.reset_advertising_id()`.
5. `ads_id` запоминает текущий ID, сбрасывает его и **ждёт, пока ID
   изменится** — успех подтверждается фактом, а не отсутствием ошибки.
6. Шаг HeyDealer повторяется; `handle_onboarding_screens()` проходит
   экраны согласия и разрешений.

`ads_id.py` работает только в настройках Google и не заходит в HeyDealer:
удаление аккаунта HeyDealer блокирует его на 3 месяца.

## Работа с интерфейсом приложений

Правила, проверенные на реальных экранах:

- **Привязка к `resource-id`, а не к тексту, подсказкам или координатам.**
  Тексты и оформление приложений меняются; если без текста не обойтись —
  поиск по частям слов.
- **Несколько алфавитов.** Системные диалоги планшета — на русском,
  приложения — на корейском. Кнопка «ОК» в русском диалоге набрана
  кириллицей и визуально неотличима от латинского `OK`, поэтому списки
  слов (`ads_id.CONFIRM_WORDS`, `CANCEL_WORDS`) содержат варианты на всех
  алфавитах.
- **Расположение кнопок — не гарантия.** В рекламной панели HeyDealer
  отказ слева, согласие справа — наоборот относительно системных
  диалогов. Такие кнопки задаются точным текстом.
- **Неожиданные экраны появляются не только при старте.** Рекламная
  панель может перекрыть результат поиска, поэтому ожидание результата
  умеет закрыть её и подождать ещё раз.
- **Неразрывные пробелы.** В корейских текстах слова разделены `\xa0`;
  перед сравнением пробелы удаляются (`re.sub(r"\s+", "", text)`).
- **Ввод текста** — только через ADBKeyBoard (`ADB_INPUT_TEXT`).
- **Carmoodo:** `appWaitActivity="*"` — заставка живёт доли секунды, и
  готовность приложения проверяется кодом.
- **HeyDealer:** работает только на физическом устройстве; уведомления
  запрещаются, чтобы всплывающее окно не перехватило нажатие.

### PARTSNUMBER

Каталог работает на виртуальной машине и доступен только как поток
изображения через VMware Horizon Blast — API и DOM нет. Распознавание:
скриншоты, многомасштабное сопоставление с шаблонами OpenCV
(`templates/`), клики по координатам и чтение через буфер обмена. Разные
марки используют разные подписи полей и форматы дат. При изменении
интерфейса координаты калибруются `calibrate_partsnumber.py`.

## Логирование и мониторинг

- У каждой проверки короткий код (`a3f19c`), который проставляется во все
  строки лога этой проверки, включая потоки Appium (через `contextvars`).
- `logs/nlc.log`: в файл всегда пишется DEBUG, в консоль — INFO.
- При непонятном экране сохраняется XML-дамп; старше 14 дней удаляются при
  старте (`diagnostics.cleanup_old_debug_files`).
- `monitor.py` раз в 5 минут прогоняет проверки и пишет администратору
  только при смене состояния (сломалось / починилось).

## Тесты

`tests/` — модульные тесты на заглушках и сохранённых дампах экранов
(`tests/fixtures/`). Оборудование, Appium и сеть для них не нужны.
Новые случаи распознавания экранов стоит закреплять тестом на реальном
дампе.
